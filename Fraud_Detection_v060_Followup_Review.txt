3. R01–R11 DISPOSITION AND REQUIRED CLOSURE

R01 — PARTIAL: ordinary hash verification improved; derived provenance remains unsound.

Observed: create_derived_subset_manifest accepts a known parent digest, an arbitrary child file, and a claimed transformation. It does not read the actual parent or verify that applying the transformation produces the child. A file containing 'not real transaction records' was consequently classified GENUINE_OBSERVED / VERIFIED_RESEARCH_DATA and acceptable for the proposal benchmark. An incorrect identity file supplied on this derived path did not cause rejection. The shipped create_verified_test_double_provenance helper can also produce provenance accepted by ModelBundle.ready.

Fix: derive subsets from verified parent bytes in a controlled, reproducible transformation, retaining source hashes, transformation/version, selection criteria, row identities, and output hashes. Verify any identity input actually used. Separate a self-declared lineage manifest from verified lineage. Keep test-only provenance out of the production acceptance path; production must reject its marker. A digest of an arbitrary child proves integrity of those bytes, not genuine transaction origin.

Acceptance: independently created arbitrary child files and test-double markers cannot become proposal-acceptable or serving-ready. A real verified-parent transformation succeeds and can be replayed to the same child hash. Missing or incorrect required identity inputs fail.

R02 — BLOCKED / PARTIAL: historical evidence absent; reconciliation can return a false success.

Observed: the reconciler accepted recorded confusion counts of 999999 when the fixture ledger had only one true positive per model. It also accepted a recorded retrain count/cost of 999999 despite an empty retrain-event list. Removing comparison metric/cost files still produced is_reconciled=true. An empty prediction ledger with headers produced a successful result with zero records and no models.

Fix: provide the actual historical manifest, prediction ledger, retrain events, timing records, configuration, provenance, and reported tables. Make strict reconciliation require the expected nonempty artifacts and strategies; validate row keys, labels, pairing, and temporal coverage. Recompute and compare all counts, totals, applicable metrics, retrain counts, and cost components. Missing data must be an incomplete/error outcome. Distinguish arithmetic reconciliation from provenance acceptance.

Acceptance: deliberately corrupt each reported count, metric, and cost independently and confirm failure. Missing artifacts and an empty run must fail. The delivered historical run must reconcile from original evidence without regenerating a replacement ledger to fit the report.

R03 — REPORTING CORRECTED; EMPIRICAL AUDIT INCOMPLETE.

H2 is now explicitly reported as unsupported. Retain that conclusion unless a new, separately versioned experiment changes the evidence. The claimed numerical results and explanation for retraining behavior remain unverified without original events and ledgers. Do not overwrite historical results with newly tuned runs.

Acceptance: trace each conclusion to delivered run IDs, event records, calculations, and prespecified hypothesis criteria; distinguish original experiments from later amendments.

R04 — PARTIAL: config files and flags exist, but actual execution differs.

Observed: invoking the pipeline with the historical config requests 150 trees and learning_rate=0.08, but the arguments passed to run_pipeline contain 100 trees and 0.1. CLI defaults overwrite configured parameters. The historical protocol_version is not forwarded and falls back to 1.0.0. Configured strategies are not forwarded. The saved resolved configuration contains conflicting nested and flattened parameters. The study CLI has no --config option, contrary to the agent's statement.

Fix: distinguish explicitly supplied CLI arguments from parser defaults. Merge defaults, file configuration, and explicit overrides once into one validated canonical configuration; execute and record that same object. Forward protocol version and strategies. Implement the promised study config support or correct the documented interface.

Acceptance: spy/integration tests assert actual estimator parameters, strategies, protocol, seed, and explicit false/default-valued overrides. Running the historical config must execute its historical parameters. Help-text checks alone are insufficient.

R05 — PARTIAL: statistical calculations have a reproduced correctness error.

Observed: the equality shortcut uses np.allclose with default relative tolerance. In a two-record software fixture, candidate probabilities [0.5000001, 0.5] and baseline [0.5, 0.5000001], with labels [1, 0], yield AP 1.0 versus 0.5. The function instead returns delta 0, confidence interval [0, 0], and empirical_p_value=0. Approximate score equality does not imply equal rankings or equal AP.

The returned tail fraction is also compared with a negative non-inferiority margin, including AP calls. That is not automatically a valid superiority p-value for a zero-null H3 claim. Identical predictions hardcode p=0. Report generation uses 200 bootstrap resamples; observing zero tails is not sufficient to report p<0.001. These issues require statistical review before relying on H1/H3 claims.

Fix: remove inappropriate approximate-equality shortcuts and recompute the requested metric. Prespecify metric, estimand, pairing, temporal blocks, margin, and hypothesis-specific inference. Validate the method against independent reference calculations and suitable null cases. State finite-resample and short-stream limitations; never convert zero sampled tails into proof of p=0.

Acceptance: the ranking fixture returns AP delta 0.5; identical, null, inferior, and clearly superior cases produce justified results. A qualified methods review confirms how confidence intervals and any p-values support each hypothesis. Recompute affected reports after correction.

R06 — PARTIAL: new quota helper works in one case; complete budget enforcement does not.

Observed: the old BaseFraudModel all-tied fixture still returns 40 alerts for budget five. The new batch helper correctly returns five. The scoring API does not apply the quota helper: eight fixture transactions returned eight REVIEW decisions despite budget-five metadata. Metadata alone is not an implemented serving quota.

Persistent online quota defects were also reproduced: after restart, replaying an admitted ID consumes another slot; a new unique ID is then denied. Returning to an earlier event day can admit two day-zero records under quota one. step=24 maps to day one in the helper but day zero in the pipeline.

Fix: define separately the classifier threshold, batch selection budget, and any promised serving admission quota. Wire the operational policy into the relevant workflow. Persist idempotency decisions and counts transactionally, use one day-boundary convention, and specify late-event handling. Ensure concurrency cannot exceed a strict quota.

Acceptance: tied scores, retries, restart, parallel requests, late events, and day boundaries all satisfy the documented policy. Research recall-at-budget must use the same declared selection semantics used in its evaluation.

R07 — PARTIAL: model controls exist; activation/promotion can lose the intended active model.

Observed: activating model family B while the configured base is A succeeds with HTTP 200, but restart restores family A. A separate controlled concurrency probe started a slow retrain from A, manually activated B, then completed the old retrain; the old job promoted A and overwrote B. Promotion did not confirm that its original active-model snapshot was still current.

Fix: use one durable authoritative activation record and explicit cross-family activation policy. Restore the accepted active model on restart. Before promotion, use a compare-and-swap check against a monotonic activation revision/epoch; reject a stale candidate. Do not rely solely on a generation number that rollback can reuse. Clearly distinguish authoritative state from best-effort aliases.

Acceptance: an accepted activation survives restart. Activation/rollback while training is in flight prevents stale promotion. Inject persistence failures and verify coherent recovery.

R08 — LARGELY CORRECTED FOR THE PREVIOUS STARTUP DEFECT; CLEANUP REMAINS.

The absent-model startup crash is fixed. The previously nonempty database password is now empty. The release still contains a .env with a default development API key and machine-local paths. This does not establish that a live deployment uses insecure settings, but it is unsuitable release hygiene.

Fix/acceptance: ship a documented .env.example, exclude runtime .env and local paths, and verify production configuration validation and readiness on the intended deployment. Startup without a model should remain NOT_READY; a verified valid model should become ready.

R09 — PARTIAL: persistent feedback improves durability; the claimed training deadline is not strict.

Observed: ThreadPoolExecutor.result(timeout=...) raises on deadline, but returning through the executor context waits for the running thread. With a 0.01-second limit and an approximately 0.08-second fit, the call returned after 0.086 seconds while recording only 0.0116 seconds and REJECTED_TRAINING_TIMEOUT. Candidate rejection works; cancellation and accurate occupied duration do not.

Fix: use an actually terminable isolated worker or a proven cooperative cancellation mechanism if a strict resource deadline is required. Otherwise describe the behavior honestly as rejecting an overrun after completion, and record actual wall time/resource use. Keep the persistent feedback improvements, and document holdout reuse and evaluation contamination controls.

Acceptance: a deliberately long fit cannot keep occupying the protected training worker beyond the defined termination grace period. Logged elapsed duration reflects reality. Durable feedback and stale-promotion tests remain green.

R10 — PARTIAL: documentation is clearer but does not establish research validity.

Corrected citations and the negative H2 statement are useful. H1/H3 numbers remain unaudited, and the statistics defect above affects confidence in generated conclusions. A research protocol containing already-known outcomes is not evidence of prospective preregistration.

Fix/acceptance: distinguish frozen protocol, dated amendments, exploratory analyses, and final results. Every numerical claim must trace to validated evidence. Separate observed transaction data from synthetic software fixtures everywhere. Discuss dataset limitations and avoid causal or generalization claims beyond the design.

R11 — PARTIAL: packaging smoke checks pass; production performance/release evidence incomplete.

The latency modes still use FastAPI TestClient in process. They do not measure actual network-service latency or establish behavior under concurrent background training. No current raw performance evidence in this delivery establishes the reported deployment numbers.

The ZIP includes old wheels, build output, and bytecode. README, deployment/test reports, and newer v0.6 claims mix versions and counts; the promised checklist is absent. Some documented test module names do not match delivered modules. GitHub tag/commit and production deployment claims were not independently verified in this review.

Fix/acceptance: create a clean reproducible release with one version, locked dependencies, manifest, checksum, current generated test report, and rollback instructions tested against that release. Benchmark a real running service with documented hardware, data shape, batch size, warm-up, concurrency, repetitions, p50/p95/p99 latency, throughput, errors, peak memory, and retraining contention. Preserve raw measurements and commands. Do not label in-process TestClient timings as network or production latency.
